## Your data is not in those folders

Your Versions, groups, migrations, restores, deployments and packages live in:

```text
garrysmod/data/vetra/blueprints/
```

This server's activation lives beside them, in `garrysmod/data/vetra/licensing/`. Leave
`garrysmod/data/vetra/` alone and everything is where you left it, **including your
activation**. The server does not re-activate and does not consume another slot.

## From 1.0 to 1.1

The same four steps. There is **nothing to migrate**: 1.1 reads your data exactly as 1.0 wrote
it, and your licence and activation are unchanged.

What you will notice is the interface: `!vblueprints` now opens a fullscreen workspace instead
of the 1.0 window. Each administrator who opens it needs the Chromium browser Garry's Mod
embeds, which Windows (any branch) and macOS have and Linux has on the x86-64 branch. See
[Compatibility](/blueprints/compatibility) and [What's new in 1.1](/blueprints/whats-new).

Delete the old folders rather than copying the new ones over them, so no 1.0 file is left
behind.

## From 1.1 to 1.1.1

The same four steps. There is **nothing to migrate**, and your licence and activation are
unchanged: 1.1.1 changes the interface only. The window and the language are settings of each
administrator's own game, saved on their computer, so nothing about them reaches the server.
See [What's new](/blueprints/whats-new).

Going back to 1.1 is the same in reverse. The display and language settings are then simply
unused, and come back if you return to 1.1.1.

## Going back to 1.0

The same steps in reverse: delete the 1.1 folders, copy the 1.0 ones in, restart. Everything
1.1 saved is readable by 1.0.

One 1.1 setting has no 1.0 equivalent: an adapter you **disabled** in 1.1 is enabled again
under 1.0, and disabled again if you return to 1.1.

## Never run two copies at once

<Warning>
Delete the old `vetra-framework` folder. Do not leave it beside the new one, under any name.
</Warning>

If more than one copy of `vetra-framework` is in `garrysmod/addons/`, **the framework does not
start at all**, and the server console names every copy it found and the version each one
declares:

```text
[Vetra] ERROR boot: 2 copies of Vetra Framework are installed, so none of them was started.
[Vetra]   addons/vetra-framework                1.1.0 (API 1)
[Vetra]   addons/vetra-framework-old            1.0.0 (API 1)
[Vetra] Keep the one folder you mean to run, normally the newest, delete the others, and restart the server.
[Vetra] Vetra Blueprints and every other Vetra product stay stopped until then. Your data in garrysmod/data/vetra/ is untouched.
```

It prints this when the server starts and again once the map has loaded. Until you fix it,
Blueprints does not open and its commands, `vetra_license_status` included, do not exist.

It refuses rather than picking one because Garry's Mod merges every addon into one file
system: two copies are two copies of the same files, and no copy can prove that the files it
would load are its own. Quietly running the wrong mix would be worse than not running.

Delete the extra folder and restart. Nothing else is needed.

## After the restart

```text
vetra_license_status
```

Should still say **ONLINE**, with no reactivation and no new slot consumed.

Open Blueprints and check the **Adapters** section: every adapter you expect should be listed
and available. Adapters for addons you do not run are listed as **Not installed** and hidden by
default; that is expected.

## Adapter compatibility across an update

An adapter records, in every Version, the format of the data it was writing. When something
later wants to act on a historical Version, Blueprints checks that the installed build of
that adapter can still read that format.

If it cannot, that domain is **blocked** in the plan with a message naming both numbers,
rather than being interpreted incorrectly. The Version itself is never altered and never
loses records.

This applies to third-party adapters as much as to the ones Vetra ships. See
[Compatibility and data versions](/sdk/compatibility) if you maintain one.
